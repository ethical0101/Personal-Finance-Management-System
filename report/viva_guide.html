2.1 Anomaly detection (the question your madam asked)

File: app/server/lib/ai.js lines 15 to 37. Called from: routes/transactions.js line 41, every time an expense is saved (manual entry or confirmed scan).

// lib/ai.js
function mean(xs) { return xs.reduce((a, b) => a + b, 0) / (xs.length || 1); }
function std(xs)  { const m = mean(xs); return Math.sqrt(mean(xs.map(x => (x - m) ** 2))); }

function detectAnomaly(newAmount, historyAmounts) {
  if (historyAmounts.length < 4)                      // MIN HISTORY = 4
    return { isAnomaly: false, zScore: 0, reason: "Not enough category history yet to judge." };
  const m = mean(historyAmounts);
  const s = std(historyAmounts) || 1;                   // guard: avoid divide-by-zero
  const z = (newAmount - m) / s;
  const isAnomaly = Math.abs(z) >= 2.5;               // THRESHOLD = 2.5
  ...
}

The three numbers that matter

ConstantValueMeaningWhy this value
Minimum history4Fewer than 4 past expenses in that category → we refuse to judgeWith 1 to 3 points the "average" and "spread" are meaningless (cold-start protection)
Threshold|z| ≥ 2.5Flag when the new amount is 2.5 standard deviations away from the category average (either direction)Chosen by simulation (table below): best balance of few false alarms and decent catching
Spread guard|| 1If all past amounts are identical, std = 0; we use 1 instead of crashingDivision safety

The formula in plain words

z = (new amount − average of that category's past expenses) ÷ standard deviation of those past expenses. Standard deviation is "the normal wobble". z tells you how many normal wobbles away from normal this purchase is. Here std is the population standard deviation (divide by n, as in line 17).

Funny exampleYour chai usually costs ₹20 ± ₹5 (the "wobble"). One day the bill is ₹2,000. Distance from normal = 1,980, and 1,980 ÷ 5 is a z of about 396. Either you bought chai at a five-star hotel, or the chaiwala's QR code is now connected to someone else's phone. Wealthline raises its eyebrow (and a notification) exactly like your mother does when she sees the Swiggy bill.

Worked example with real arithmetic

Groceries history: 900, 1500, 1100, 1800, 1300, 1600. Mean = 1,366.67. Population std = 303.68. Flag line = mean + 2.5 × std = 1,366.67 + 759.2 = ₹2,125.87.

What happens when flagged: the transaction is saved with flaggedAnomaly: true and its anomalyZScore (transactions.js line 46); a notification is inserted ("Unusual Groceries transaction of ₹... — This transaction is 7.0x the typical spread for this category (avg ₹1367)"); the Insights page lists the 5 latest flagged items as "critical" recommendations; the Health Score loses 5 points per flagged item this month; and the Ask AI snapshot includes the last 5 flagged items.

The demo case: in the demo account a ₹9,800 grocery bill shows z = 76.42, because the account's normal groceries are very steady, so the "wobble" is tiny.

Why 2.5? (evidence, not opinion). Script: app/server/scripts/evaluate_models.js, seed 20261026

We simulated 300 users × 200 transactions, injecting 10% anomalies, and tried three thresholds (results stored in analysis/eval_models.json):

ThresholdPrecisionRecallF1False-alarm rate
2.096.1%72.4%0.8260.34%
2.5 (chosen)98.4%63.1%0.7690.11%
3.099.4%53.5%0.6960.04%

Precision = of the things we flagged, how many were truly unusual. Recall = of all truly unusual things, how many we caught. In a finance app a false alarm annoys users and makes them ignore alerts, so we favour precision (98.4%) over catching everything. Recall by size of the spike at 2.5: spikes of 1.5 to 2 times normal are caught only 6.7%; 2 to 3 times 28.1%; 3 to 5 times 94.9%. So "we catch big, obviously unusual spends reliably; subtle ones we deliberately leave alone."

Say this if asked "why not 2 or 3?""At 2 we catch more but false alarms triple (0.34% vs 0.11%). At 3 we are almost never wrong but we miss nearly half. 2.5 is the knee of that trade-off, and we measured it, we did not guess."
Known weakness (admit it)A huge past outlier inflates the standard deviation and can hide later ones (called masking). A robust version would use the median and MAD. Also, anomaly is per category and amount only: it does not look at time of day, merchant or location.

2.2 Next-month forecast: exponential smoothing

File: lib/ai.js lines 60 to 76. Used by the Insights page, the "forecast over budget" recommendation, the what-if simulator and the Ask AI snapshot.

const SMOOTHING_ALPHA = 0.4;
function forecastNextMonth(transactions) {
  const series = monthlyTotals(transactions);            // total spend per month, oldest first
  if (series.length === 0) return { forecast: 0, method: "none", confidence: "low" };
  if (series.length < 3) return { forecast: mean(series), method: "average", confidence: "low" };
  let level = series[0].total;
  for (const { total } of series.slice(1))
    level = 0.4 * total + 0.6 * level;                   // the whole algorithm
  return { forecast: Math.max(0, level), method: "exp-smoothing",
           confidence: series.length >= 6 ? "medium" : "low" };
}
ConstantValueMeaning
alpha0.4How much weight the latest month gets (40%); the history so far gets 60%
Minimum months3Under 3 months we just use the plain average and mark confidence "low"
Medium-confidence cut6 months6 or more months of data → "medium"; never "high" because it is only a statistical smoother
Floor0A forecast can never be negative

Worked example (monthly grocery totals 100, 120, 110, 130, 125, 140; in ₹ hundreds): start level = 100; then 0.4×120+0.6×100 = 108.0; then 0.4×110+0.6×108 = 108.8; then 0.4×130+0.6×108.8 = 117.28; then 0.4×125+0.6×117.28 = 120.37; then 0.4×140+0.6×120.37 = 128.22. So next month is forecast at about 128 (the latest 140 is pulled back toward the trend, which is what smoothing is for).

Funny examplealpha = 0.4 means: "40% believe last month's gossip, 60% believe the old wisdom." If you set alpha = 1 you believe only last month, like a friend who thinks one good IPL match makes a team world champions. If alpha = 0 you never update, like an uncle who still thinks petrol is ₹60.

Why smoothing and not regression? (we tested)

Original code used a linear-regression line. We measured MAPE (average percentage error) on 300 synthetic series × 8 forecasts = 2,400 forecasts:

MethodMAPE
Exponential smoothing (alpha 0.4)13.76%
3-month moving average14.05%
Linear regression15.95%
Naive (copy last month)17.04%

Smoothing beat regression in 60% of series and naive in 63.4%. It also won on rising, flat and falling trends. So we replaced regression with smoothing. MAPE = mean of |actual − forecast| ÷ actual, as a percent.

Honest noteAlpha 0.4 was a reasonable fixed choice, not tuned per user. The 3-month moving average is almost as good (14.05%); smoothing wins mainly on robustness and simplicity. Evaluation data is synthetic, so say "on simulated series".

2.8 Bill scanning pipeline (all the checks)

Files: routes/scan.js, lib/gemini.js, web ScanView.jsx. Eight steps:

  1. Photo in the browser: downscaled before upload; the server accepts only JPEG, PNG or WebP and rejects over 4,000,000 base64 characters (about 3 MB) with HTTP 413.
  2. Cache check: key = hash(photo + category names); scan results live 30 days. Same photo = no new API call.
  3. Gemini vision returns JSON: merchant, date, total, currency, category (must be one of the user's own categories), up to 8 line items, confidence 0 to 1. Temperature 0.1 (near-deterministic), thinking budget 256, max 1,500 output tokens, timeout 45 s.
  4. Not a bill? Gemini returns not_a_receipt → we answer HTTP 422.
  5. Total check: must be a positive number, else 422.
  6. Date sanity: if the date format is wrong we use today; if the bill is more than 400 days old or more than 7 days in the future we show "Check the date" (catches two-digit-year mistakes such as 18-10-26).
  7. Budget impact: spent-before + bill total = spent-after; percent before and after; "over by" amount (all computed by our code, not by AI).
  8. Duplicate check: an existing expense on the same date with amount within ₹0.01 → "possible duplicate". The user always confirms before anything is saved, and the confirmed save goes through the normal transaction route, so anomaly detection runs on it too.

Measured accuracy (scripts/evaluate_scan.js, analysis/eval_scan.json): 10 labelled bills plus 1 non-bill. Total exact: 100%; category: 100%; date: 90%; merchant: 90%; all four correct: 90%; the one wrong date was caught by the date check (1/1); non-bill rejected (1/1). Mean latency 157 ms (cached repeat; a first call takes several seconds).

Funny exampleGemini is a very fast intern who reads handwriting. We are the manager who checks: "date says year 1926? Sir, were you shopping in the British era?" (date check), "you already paid this biryani yesterday" (duplicate check), "this will blow your Dining budget" (impact). The intern never signs the cheque; you do.

3.1 GQ(I)M: Goal, Question, (Indicator), Metric

A top-down plan: start from a goal (e.g. "make financial advice trustworthy"), ask questions ("how often do users accept recommendations? how wrong is the forecast?"), and attach a metric to each. The app really logs these: accept/dismiss clicks are stored as recommendation-event notifications (insights.js line 135), which feeds the Recommendation Acceptance Rate; forecast error is MAPE (measured above); transaction failure rate is the control-chart metric. Why GQ(I)M: otherwise teams collect numbers nobody needs.

3.3 I-MR control chart (analysis/analyze.py lines 218 to 227)

x = weekly transaction failure rate (%)           16 weeks
MR = |x[i] - x[i-1]|                                moving range (week-to-week change)
CL     = mean(x)              = 3.517
UCL_I  = CL + 2.66 * mean(MR)  = 6.556
LCL_I  = max(CL - 2.66 * mean(MR), 0) = 0.477
UCL_MR = 3.267 * mean(MR)

Where 2.66 and 3.267 come from: standard control-chart constants for subgroup size 2. 2.66 = 3 ÷ 1.128 (1.128 is the constant d2 that turns an average moving range into an estimate of sigma, so the limits are 3-sigma); 3.267 is the constant D4 for the moving-range chart. Result: week 12 (7.48%) breaches the UCL of 6.556: the simulated release regression. Weeks 11 and 13 (5.76, 5.71) are high but inside the limit.

Funny exampleHostel mess quality: some days the dal is thin, some days thick, that is normal variation. Then the cook changes and every day is a disaster. The control chart is the mess committee that can tell "normal Tuesday dal" from "the cook was replaced".

3.5 Bayesian network (analysis/bayesian_network.py)

A small cause-and-effect graph: Requirement Volatility (R) and Team Experience (T) influence Schedule Delay (S) and Defect Density (D), which influence Project Risk (P). Priors: P(R=High)=0.45, P(T=High)=0.60. Hand-specified conditional probability tables; exact inference by enumeration (Bayes theorem). Results for P(Project Risk = High): baseline 28.1%; worst case (volatile requirements + inexperienced team) 55.0%; best case 12.8%; if delay is already observed High 50.0%; if defect density is observed High 49.1%. The same tables are re-implemented in the Metrics Deck so the risk calculator is live.

Funny exampleYou hear "the exam paper is leaked" (evidence). Your belief you will pass changes. A Bayesian network is that updating, but done with numbers. Worst case in our network is "changing requirements + freshers", which is every group project in the last week.
Honest noteThe conditional probability tables are hand-specified from the module data distribution, not learned from a large dataset. Say "illustrative, expert-elicited".

Part 6: Questions faculty may ask, and answers

Q1. How do you detect anomalies in the budget? Show the threshold in the code.

Open lib/ai.js line 29. We compute z = (amount − category mean) ÷ category standard deviation and flag when |z| ≥ 2.5, but only if the category has at least 4 past expenses. 2.5 was chosen from a simulation of 300 users × 200 transactions: precision 98.4%, recall 63.1%, false-alarm rate 0.11%; thresholds 2 and 3 were worse trade-offs.

Q2. What is a z-score and why use it?

The number of standard deviations a value is from the mean. It is unit-free, cheap, explainable to a normal user ("7x the usual spread") and needs no training data, which matters because each user starts with no history.

Q3. Why not machine learning for anomalies (isolation forest, autoencoder)?

A new user has 0 to 20 transactions; ML needs far more. A z-score works from 4 points, is explainable and runs inside a serverless function. ML is listed under future work once enough data exists.

Q4. Is the anomaly check per user or global?

Per user and per category (history is filtered by userId and categoryId, transactions.js lines 38 to 40). Rent of ₹18,000 is normal for Rent and not compared with Groceries.

Q5. What are the weights in your health score and why?

40 savings rate, 30 budget adherence, 15 no unusual spending, 15 goal progress, total 100 (dashboard.js lines 26 to 46). Savings gets most weight because it is the outcome that matters; budget adherence is the habit that causes it; the other two are supporting signals. They are a transparent design choice and are shown component by component in the UI; they are not learned.

Q6. How is the forecast computed and how accurate is it?

Simple exponential smoothing, alpha 0.4, on monthly category totals; below 3 months it uses the average and says "low" confidence. On simulated data MAPE is 13.76%, better than regression 15.95%, moving average 14.05% and naive 17.04%.

Q7. Why alpha = 0.4?

It balances reacting to a real change (higher alpha) with ignoring one-off noise (lower alpha). We fixed it for transparency and validated the resulting method against alternatives. Tuning alpha per user is future work.

Q8. Which software metrics did you use, and how do they appear in the system?

Product metrics (complexity, CBO, LCOM, coverage, defect density) for the decision tree and correlations; process metrics (weekly transaction failure rate) for the I-MR chart; AI-quality metrics (MAPE of forecast, precision/recall of anomaly detection, recommendation acceptance rate, scan field accuracy). The last group are measured on the real code and logged by the real system; they are the GQ(I)M "metrics" in practice.

Q9. Is your data real?

The finance data in the demo is seeded sample data. The module/sprint metrics are synthetic, generated for the course by analysis/generate_data.py. The evaluation of forecast and anomaly methods uses seeded simulation (seed 20261026) so anyone can reproduce it. Scan accuracy uses 10 labelled bill images in report/eval_receipts.

Q10. Which AI API do you use? Is the user's data safe?

Google Gemini REST API only (model chain gemini-3.6-flash → 3.5-flash → 3.1-flash-lite → 2.5-flash). Bill photos are processed in memory and not stored. Ask AI receives only a compact summary of that user's own data (15 latest transactions plus aggregates). Key is a server environment variable, never in the repo.

Q11. What if Gemini is down or the quota ends?

The model chain falls back to the next model; results are cached (30 days for scans, 1 day for advice); the functions never throw, they return a reason, and the UI shows a friendly message and the manual add path. The formula-based features (anomaly, forecast, score) do not depend on Gemini at all.

Q12. How do you stop the AI from making up numbers on a bill?

Temperature 0.1, a strict JSON format, and our own checks: the total must be positive, the date is sanity-checked (over 400 days old or over 7 days ahead is flagged), duplicates are detected, and the user must confirm and can edit every field. We measured 100% total accuracy and 90% all-fields on 10 labelled bills.

Q13. Explain the control chart limits.

Centre line is the mean failure rate 3.517%. UCL = CL + 2.66 × average moving range = 6.556%, LCL = 0.477%. 2.66 = 3 ÷ d2 (1.128). A point outside the limits (week 12 at 7.48%) signals a special cause, not normal variation.

Q14. Your decision tree has 91.7% accuracy; is that good?

That is training accuracy and over-optimistic. Leave-one-out accuracy is 58.3% against a 50% baseline, so it is only mildly better than guessing, as expected with 12 modules. Its value is explanation (LCOM importance 0.918), not prediction.

Q15. Why three correlation coefficients?

Pearson assumes linearity and is sensitive to outliers; Spearman uses ranks; Kendall counts concordant pairs and suits tiny samples. When all three agree on direction (as for complexity vs defects) the conclusion is more trustworthy.

Q16. How is the budget affected when a bill is scanned?

The server finds that category's budget for the bill's month, adds the bill total to month-to-date spend, and returns before/after percentage and the overspend amount. The scan alone changes nothing; only Save does.

Q17. How do you secure user accounts?

bcrypt (cost 10) hashed passwords, JWT with 7-day expiry, per-user data filtering on every query, positive-amount validation, password-confirmed account deletion.

Q18. How did you test it?

A 48-check automated smoke test (local and production, all pass), a labelled bill evaluation, a model evaluation script with fixed seed, and responsive-layout audits at six screen widths (1920 to 360 pixels).

Q19. What is the architecture?

React single-page app on Vercel → one serverless Express function (/api) → MongoDB Atlas; Gemini called only from the server; Python scripts produce the metrics analysis and the embedded dashboard offline.

Q20. What is novel here?

(1) Scan → budget-impact preview before saving; (2) every score is a visible formula; (3) the AI layer is measured with software-metrics methods (precision/recall, MAPE, acceptance rate, control chart) instead of just being used; (4) the project's own engineering metrics live inside the product.

Q21. What would you improve?

Use robust statistics (median/MAD) for anomalies; per-user alpha tuning; real production metrics instead of simulated ones; add recurring-bill auto-posting, multi-currency and bank import; learn the health-score weights from user outcomes.

Part 7: Honest limitations (say these first)

  • Synthetic metrics data: module and sprint metrics, and the forecast/anomaly simulations, are generated. Methods are real; absolute numbers are illustrative.
  • Small-sample decision tree: 12 modules; LOOCV 58.3% only slightly beats the 50% baseline.
  • Z-score masking: large past outliers inflate the standard deviation and can hide later anomalies; spikes under 2x normal are mostly not caught (recall 6.7% for 1.5 to 2x).
  • Fixed hyper-parameters: alpha 0.4, threshold 2.5 and the health weights are fixed by design, not personalised.
  • Gemini dependency: scanning and advice need a working API key and free-tier quota; first call can take up to 25 seconds. Results are cached and fallbacks exist.
  • Scan accuracy sample: only 10 labelled bills; date and merchant were 90%, not 100%. Real-world messy photos may do worse.
  • Bayesian network tables: hand-specified, not learned.
  • Camera: live webcam path tested only up to the permission prompt in automation; confirm once on a real laptop before the viva.
