Review Talking Points

Plain-language script for explaining Modules 3 & 4 to your reviewer — read it once before, glance at it during.

1. The 30-second opener

Say this first "We built a personal finance app. On top of that, we tracked software metrics on it the way a real engineering team would — how many bugs each part has, whether the project is on schedule, and how risky it is. Module 3 is us collecting and analyzing that data. Module 4 is us using it to predict and manage risk."

2. "Where did this data come from?"

If she asks this — say "Our app doesn't have real users yet, so we generated a realistic dataset for 12 parts of the app — like Login, Transactions, the AI engine — across 16 weekly sprints. It's not random: we built in the same relationships a real project shows, like 'messier code tends to have more bugs.' Then we ran the exact same analysis on it that a real team would run on real data."

4. Module 3 walkthrough (what to click, what to say)

1
Click: Data Collection tab
"Here are our 12 modules. For each one we track four things — and these four words are not the same thing:"
ErrorA person's mistake — like misreading a requirement.
Fault / BugThe wrong code that mistake caused.
DefectA bug that QA actually caught and logged.
FailureA defect that actually broke something for a real user.
"So a bug can sit quietly in the code for months — it only becomes a failure once a user actually hits it."
2
Click: Analysis Techniques tab
Decision Tree"This is a flowchart that guesses whether a module is high-risk or low-risk just from its code stats. It got it right 91.7% of the time on our data."
Box Plot"This just shows the spread — are most modules similar, or is one badly sticking out?"
Control Chart"This is the same tool factories use to catch a machine going out of whack. We ran it on our weekly failure rate, and it correctly caught the exact week we simulated a bad release."
Correlation — 3 types"We checked if messy code (complexity) really is linked to more bugs — three different statistical ways, so one method alone can't mislead us with such a small dataset. All three agreed: yes."
If she asks "why three correlation types?"
PearsonDo the two numbers move together in a straight line?
SpearmanDo they move in the same direction, even if not a straight line?
KendallOut of every possible pair of modules, how often does "more complex" also mean "more bugs"? The most cautious of the three — best for a small dataset like ours.

6. Likely questions — quick answers

Why generated data instead of real data?
Our app has no real user history yet. We simulated a realistic 12-module, 16-sprint dataset with the same statistical relationships a real project shows, then ran identical analysis to what we'd run on live data.
What's a Bayesian Network in one line?
A probability calculator built from a small network of "if this, then that" tables — give it evidence, it updates its guess.
What does "risk overcome, idea only" mean?
For each risk we found, we wrote one concrete mitigation idea — e.g. pair a junior developer with a senior reviewer on the riskiest module — without building the full process around it.
Where does the Metrics tab live?
It's not a separate document — it's served by our own app server and embedded as a tab inside the finance app itself, so it's one click away from the product it's measuring.
