Bill-Scanning Pipeline — from photo to budget decision
1CaptureCamera / upload / sample bill. Resized in the browser
2ValidateJWT · type (JPEG/PNG/WebP) · size ≤ 3 MB · fetch the user's categories
3Cache lookupSHA-256(image + categories) in MongoDB — a hit returns in about 150 ms and uses no quota
4Gemini visionModel fallback chain, JSON mode; returns merchant, date, total, category, items; rejects non-bills
5Sanity checksTotal > 0 · date format · date within about 400 days · duplicate (same date and amount)
6Budget impactSpent before/after, % of limit, over-by amount for that category and month
7ConfirmUser edits and saves → transaction, balance, alerts
Why this design: the model only reads the bill; every consequence (budget impact, duplicates, anomaly check after saving) is computed by deterministic server code, and nothing is saved until the user confirms. The image is processed in memory and never stored.
